半年前我把 `tar -czf dist.tgz dist` 写进了 deploy.sh,然后开始把所有看起来繁琐的工作都甩给 Claude Code。三个月后,我拿回来了一半。

不是 Agent 不好用。是有些事,我原本就没搞清楚为什么要做。

## 留下的六件事

第一件,样板代码。CRUD 模板、DTO 转换、测试夹具——这种代码我写过几百遍,每写一遍还要先说服自己「这次能不能跳过」。现在我跳过,因为我知道这玩意儿的正确写法长什么样,我只是不想再打一遍。Agent 写得比我快,跟我写得一模一样。

第二件,git commit message。这事儿过去经常让我烦躁——代码改完,想 commit,盯着 vim 三分钟想不出怎么总结。Agent 看一眼 diff,写一段规整的「feat / fix / refactor: xxx」,我偶尔改一个字就提交了。我省下来的不是时间,是「又被打断一次」的挫败感。

第三件,找文档。官方文档那些藏在角落的参数,Google 经常搜不到,要用文档站自带搜索。Agent 会帮我定位到具体的 API 段落,顺便告诉我哪段已经 deprecated。这件事我自己做要十分钟,Agent 做一分钟。

第四件,单元测试的 happy path。我知道这段代码应该测什么,但写测试本身不增加信息。让 Agent 写 happy path,我补 edge case。节奏顺了。

第五件,数据迁移脚本。Schema 已知的时候,迁移脚本是一种「翻译工作」,没有创造性。Agent 写得比我细致,会主动加 IF NOT EXISTS 之类的保护。

第六件,文档校对。错别字、不通顺、标点不一致——这是 Agent 做得最稳的活儿之一。我写过一篇散文,Agent 帮我抓出了七个错别字,自己看了三遍都没发现。

## 拿回来的四件事

第一件,架构决策。一个 service 该不该拆?一个表该不该分?改了之后三个月才知道对不对,Agent 当时不知道,我也经常不知道。这种事我必须自己做,而且要带着「我承认可能错」的心态做。让 Agent 帮我做决策,等于把「错了我能学到东西」这件事外包出去——亏。

第二件,debug 莫名报错。尤其是「本地能跑,线上 500」这种。报错栈读起来头都大,Agent 给出的解释有时候对,有时候错在对的地方,根因在另一个文件。我现在不直接信 Agent 的 debug,把它给的线索当线索,自己顺着走。debug 是「在黑暗里摸东西」,Agent 的手感和我的不一样。

第三件,写「立秋后的茶事」。这件事下一篇展开,但提前说一句:Agent 能写,但写得不对。它写得「像散文」,写得「有调性」,但读起来不是「我」。这种工作我不能外包,因为读者读的是我的眼光,不是修辞。

第四件,读别人代码。读代码本身不能跳——读懂了才能在 PR 里讨论,才能在生产环境排查时不慌。Agent 可以给我一个「这段代码在干什么」的三句话总结,但它不能代替「我读懂了」这件事。读懂了和「知道它在干什么」是两码事。

## 一个判断标准

这件事如果我解释不清为什么这么做,Agent 也帮不了。

这是我这三个月摸出来的标准。比工具清单更有用的是这个问题:「如果 Agent 写错了,我能不能发现?」能发现,就能外包;不能,就别外包。

写样板代码我当然能发现——这玩意儿对就是对,错就是错。debug 报错我不能保证发现——Agent 解释得通,但根因可能在另一个文件,我没有「一眼看出对错」的能力,就别让它做。

标准不是「Agent 能不能做」,是「我有没有能力验证」。验证能力比工具能力稀缺。

## 收尾

不是「用了 Agent 就高级」。是把精力放在值得花的地方——值得花的地方,通常是我解释不清为什么要做的事。

我拿回来的那一半,才是我作为开发者的真正工作。剩下那一半,Agent 是我的助手,不是我的替代。

---

写完这篇,我又打开了一个待办:让 Agent 帮我把 deploy.sh 的注释校对一下。它校得比我仔细。

但下次架构调整,我得自己想。
